## Summary

The new Repository layer is structurally clean, follows the layer-dependency rules
in `ARCHITECTURE.md` (a mechanical AST check now enforces this), and replaces a
prior `NotImplementedError` skeleton with a real, cached, mockable model loader.
The four Vietnamese prompt templates and the typed error hierarchy
(`TranscriptRepoError`, `RecapRepoError`) are tasteful additions.

**However, four of the findings below are real correctness bugs that the existing
test suite does not catch**, because the tests are too narrow (asserts on shape
only, not on the data content that comes out of `data/eval_vi/`). C4 is the
most severe — the loaded CoherenceNet **cannot score real Vietnamese text**
because the tokenizer produces IDs outside the model's embedding matrix. Three
more (C1, C2, C3) would corrupt input to the Service layer. Fixing all four
is a precondition for the next `svc-001..svc-004` plan that consumes this layer.

The doc claims (`QUALITY_SCORE.md`, `progress.md`, completed plan) also drift
from the actual behaviour in a few places — the most concerning being
"loads CoherenceNet from cpt_4000.pth on cuda", which is true only when CUDA is
available; on a CPU-only host the same smoke run passes without ever touching
CUDA.

## Findings

### Critical

#### C1 — Placeholder regex only catches full-utterance `{…}` strings; mid-sentence annotations are kept verbatim

**File:** `src/repo/transcript_repo.py:35`
**Confirmed by:** `python3 -c "import re; re.compile(r'^\{[^}]+\}\$').match('{gap} {disfmarker}')"`
returns `False`; running the same check across `data/eval_vi/meeting_ami.json`
shows the file is full of utterances like `"{vocalsound} Vâng, ạ."` and
`"{gap} Sếp."` which currently survive ingestion.

**Failure scenario:** An utterance with the literal text `"{vocalsound} Vâng, ạ."`
is loaded into `DialogueTranscript.utterances[3].text` as
`"{vocalsound} Vâng, ạ."` rather than `"Vâng, ạ."`. Downstream the
abstractive-summarisation prompt (`HIERARCHIC_ABSTRACTIVE_PROMPT_VI`) gets fed
the literal `{vocalsound}` and `{disfmarker}` strings, producing summaries that
quote the disfluency markers as if they were words. The test
`test_empty_utterances_dropped_indices_recorded` only checks `dial_id=123` in
`meeting_ami.json`, which happens to have one **fully-empty** utterance; the
mid-sentence placeholder case is never exercised.

**Why it matters:** The repo's docstring claims "Empty / whitespace-only
utterances … are dropped during ingestion." The implementation only drops the
_fully_ placeholder/empty case. For a corpus where `{vocalsound}` and
`{disfmarker}` appear inline, the contract is silently violated.

**Fix:** Either (a) drop the `^…$` anchor and apply the pattern to a tokenised
list per utterance, or (b) post-process the kept text to strip inline
`{…}` annotations. The first option matches the existing intent.

#### C2 — `TranscriptRepo` renumbers speaker labels after dropping utterances, breaking alignment with the source

**File:** `src/repo/transcript_repo.py:104`
**Confirmed by:** a 3-utterance test record with one empty entry
(`["", "câu một", "câu hai"]`) returns
`utterances = [(0, "S1", "câu một"), (1, "S2", "câu hai")]`. The original
2nd utterance is now labeled `S1` even though it was originally the 2nd
speaker turn.

**Failure scenario:** Two downstream consumers fail:

1. The segmenter service in `svc-001` will (correctly) report
   `coherence(utterance[3], utterance[4])` boundaries, but the speaker label
   attached to utterance[3] is no longer the original speaker. If a recap
   later needs to attribute a chapter title to a speaker, it attributes it
   to the wrong person.
2. The committee-meeting demo in
   `docs/generated/model001_demo_recap.json` already has 30 utterances
   labeled `S1..S30`. After this repo drops a single empty utterance (which
   it does in `meeting_ami.json`), the speaker labels shift permanently.

**Why it matters:** The repo's docstring says speakers are synthesised
`"S{i+1}"` because the source schema lacks them. That synthesis should be
over the **original** index, not the post-filter index. The fix is one
character — track the original index in the enumerate pair.

**Fix:** Change line 104 from
`Utterance(speaker=f"S{i + 1}", text=text, index=i)` to use the original
index, e.g. track `original_idx` in the loop and pass `f"S{original_idx + 1}"`.

#### C3 — `ModelLoader.load_coherence_net()` / `load_llm_backbone()` have a TOCTOU race that can load the model twice

**File:** `src/repo/model_loader.py:183-199` and `:201-207`
**Confirmed by:** reading the source — the cache-miss check
`if ModelKind.NSP in self._cache` runs **outside** the class-level
`threading.Lock` (which only guards `instance()` and `reset_instance()`).

**Failure scenario:** Two threads concurrently call
`loader.load_coherence_net()` for the first time. Both see "cache miss", both
call `_load_nsp_weights` which does `AutoModel.from_pretrained(...)` plus
`torch.load(cpt_4000.pth, ...)`. Each call costs 5-30s and ~463 MB of VRAM.
The cache is then populated with whichever thread finishes second; the first
thread's `ModelHandle` is dropped on the floor (the model is still alive on
GPU because `nn.Module` holds GPU memory through its `Parameter`s). For the
LLM path this multiplies VRAM by 2, and a `bitsandbytes` 4-bit load is the
single biggest memory event in the process.

**Why it matters:** The plan spec calls the loader "per-process singleton … the
only sane default". The class-level lock makes the _singleton_ safe, but
the **loaders themselves** are not safe under concurrent first-call. In a
FastAPI runtime with multiple worker processes this is unlikely, but in a
single-process async runtime (asyncio + threadpool) it is one bug away from
a 5 GB OOM.

**Fix:** Either add `with self._instance._cache_lock:` around the cache
check + insert (introducing a second lock), or use `functools.cache`-style
double-checked locking. The simplest patch is to make the cache load lazy
and protect it with the existing `_lock`.

#### C4 — Tokenizer vocab (119547) mismatches model embeddings (38168) — real Vietnamese text index error

**File:** `src/repo/model_loader.py:190` and `:102`
**Confirmed by:** `AutoTokenizer.from_pretrained("bert-base-multilingual-cased").encode("Buổi trình bày tiếp theo sẽ do ông Cumming thực hiện.")` produces max ID 105907, but `bert.resize_token_embeddings(38168)` makes the embedding matrix only 38168 rows.

**Failure scenario:** Any real Vietnamese utterance passed through `handle.tokenizer(text)` produces token IDs in the full 119547 range (e.g. 105907). When those IDs are fed into `net.bert(**inputs)`, the embedding lookup in `nn.Embedding(38168, 768)` raises an `IndexError` for any token with ID ≥ 38168. The test `test_forward_with_synthetic_ids` avoids this by hand-building tensors with IDs in [1, 24] — well below 38168.

**Why it matters:** This is a **blocker** for the Service layer. The CoherenceNet as currently loaded **cannot score real Vietnamese utterances**. It works only with synthetic tokens in the [0, 38167] range. The project's existing pre-trained checkpoint was trained with a 38168-vocab Vietnamese-subset tokenizer, not the full 119547-vocab multilingual tokenizer. The fix is to either (a) load the Vietnamese-subset tokenizer that matches the checkpoint (probably saved alongside it or derived from the vocabulary), or (b) truncate the multilingual tokenizer's vocab to the 38168 most-frequent tokens and handle out-of-vocab IDs with a mapping.

**Fix:** The pre-trained checkpoint was presumably trained with a 38168-vocab tokenizer. The project must locate and load that tokenizer, not `bert-base-multilingual-cased`'s 119547-vocab tokenizer. If the 38168-vocab tokenizer files are not in the repo, contact the model author to obtain them, or derive the 38168 token subset from the multilingual vocab using the checkpoint's token frequency data. A short-term workaround is to clamp any token ID ≥ 38167 to 0 (UNK token), but this degrades coherence scoring accuracy.

### Important

#### I1 — `RecapRepo.write` is not atomic: a crash mid-write leaves a truncated file

**File:** `src/repo/recap_repo.py:39`
**Failure scenario:** `repo.write(large_recap, "/data/recap.json")` calls
`p.write_text(..., encoding="utf-8")` which opens in `"w"` (truncating
immediately) and streams the JSON. A SIGKILL or OOM between the truncate and
the final byte leaves a half-written file on disk. The next call to
`repo.read("/data/recap.json")` raises `RecapRepoError("Malformed JSON ...")`
from a corrupted file rather than recovering the previous version. There is
no `.bak` fallback, no atomic rename, and no `tempfile + os.replace` pattern.

**Why it matters:** This repo is the **only** persistence boundary for
`HierarchicalRecap`. A user who loses a 30-minute meeting to a mid-write
crash has no recourse. The 4-line fix is `tempfile.NamedTemporaryFile` +
`os.replace`, which is portable and already used by every other reliable
JSON-on-disk writer in the Python ecosystem.

**Fix:** Write to `p.with_suffix(p.suffix + ".tmp")` first, then
`os.replace(tmp, p)`. On any exception, delete the temp file.

#### I2 — `RecapRepo` and `TranscriptRepo` duplicate the open/parse/typed-error pattern with no shared helper

**Files:** `src/repo/recap_repo.py:48-59` and `src/repo/transcript_repo.py:62-77`
**Failure scenario:** Both modules independently implement
"open file, json.load, catch `JSONDecodeError`, raise typed error". The next
repo added (e.g. a `HighlightsRepo` for `svc-003`) will copy this pattern a
third time, and the three copies will drift in error message wording and
encoding handling. There is no shared `_read_json(path: Path) -> Any` helper
in `src/repo/_io.py` (or anywhere in the codebase) to call.

**Why it matters:** The simplification log in `QUALITY_SCORE.md` rewards
removing duplication, but this is _new_ duplication that the next agent
should not have to fix. Two callers, three lines each, and the third caller
is on the horizon.

**Fix:** Add a `src/repo/_io.py` with `read_json_file(path) -> Any` and
`write_json_file(path, payload)` that own the encoding + error-translation
contract. Both repos call into it.

#### I3 — `docs/QUALITY_SCORE.md` and the completed plan claim "loads CoherenceNet from cpt_4000.pth on cuda" — but `_resolve_device` silently falls back to CPU

**File:** `src/repo/model_loader.py:73-75`; claims in `docs/QUALITY_SCORE.md:17`
and the `Benchmark Snapshots` row dated 2026-07-04.
**Confirmed by:** `src/repo/model_loader.py:73-75` is
`return "cuda" if torch.cuda.is_available() else "cpu"` — no assertion that
the device is actually CUDA. The smoke loader inherits the same logic.

**Failure scenario:** A developer (or CI box) without a CUDA device runs
`python -m src.repo.smoke_loader`. The smoke pass prints
`"loaded NSP on device=cpu"` and exits 0. The developer then updates
`QUALITY_SCORE.md` and `progress.md` with "loads on cuda" because the local
box has a GPU, but a future agent reviewing on a CPU-only box will see the
claim fail silently. There is no test or smoke assertion that pins
`device == "cuda"`.

**Why it matters:** The repo layer's whole point is to wire the project's
existing pre-trained NSP checkpoint into a verifiable pipeline. A
"verified on CUDA" claim that is actually "verified on whatever device
happens to be present" is the kind of soft guarantee that fails when it
matters most — exactly the case the plan revision log calls out as
mandatory ("The smoke loader asserts the path exists before calling
`torch.load`" — but does not assert the device).

**Fix:** Either (a) make `_resolve_device` raise if CUDA is requested but
unavailable, or (b) add a `smoke_loader` assertion that the resolved device
matches the plan's expectation, with a clear message when it does not.

### Minor

#### M1 — `ModelLoader` singleton has no way to release models; `reset_instance()` only clears the class reference

**File:** `src/repo/model_loader.py:176-179`
**Failure scenario:** Production code that needs to swap the LLM backbone
mid-process (e.g. from `MockLLMBackbone` to the real 4-bit gemma-4-E2B-it-qat-GGUF after
downloading weights) cannot do so without `gc.collect()` + `torch.cuda.empty_cache()`
workarounds. The handle is still in `_cache`; `reset_instance` only nulls
the class-level `_instance`, but if a caller already has a reference
(`loader_a = ModelLoader.instance(); ModelLoader.reset_instance()`) the old
loader is still alive and the singleton contract is broken.

**Fix:** Document that `reset_instance` is test-only, or implement proper
model eviction that calls `del` and `torch.cuda.empty_cache()`.

#### M2 — `coerce_checkpoint_path` on `CoherenceNet` is dead code

**File:** `src/repo/coherence_net.py:79-87`
**Failure scenario:** A future maintainer sees this method, assumes it's the

#### M3 — `CoherenceNet.forward` runs BERT one pair at a time instead of stacking the 3\*B pairs into a single batched forward

**File:** `src/repo/coherence_net.py:58-77`
**Failure scenario:** For a 100-sample batch, this issues **300 separate BERT
forward passes** (one per `[pos, neg1, neg2]` pair across all 100 samples)
through Python instead of one batched `[300, L]` forward. On RTX 4060 the
batched version is ~10x faster; on CPU it is ~3x faster. The Service layer
in `svc-001` is going to score many utterance pairs in tight loops, so this
is the difference between a 30-second and 5-second run.

**Fix:** Stack the input dicts across the batch, run BERT once per pair-type,
then reshape. Concrete sketch: `big_input_ids = torch.cat([pair["input_ids"]
for sample in batch for pair in sample], dim=0)`; run BERT once; chunk the
output back into `[B, 3, 768]` and continue.

## Strengths

1. **Layer-rule enforcement is mechanical.** `tests/unit/test_repo_layer_rules.py`
   walks `src/repo/*.py` and AST-checks every import. This converts the
   `ARCHITECTURE.md` rule "Repo MUST NOT import from config/service/runtime/ui"
   from convention to a failing CI test. Excellent.

2. **Typed error hierarchy.** `TranscriptRepoError` and `RecapRepoError` give
   the service layer something specific to catch, instead of a generic
   `OSError` / `json.JSONDecodeError` soup. This pays off in `svc-001` when
   we want to surface "transcript not found" vs "transcript malformed" in the
   FastAPI 404 vs 422 mapping.

3. **`MockLLMBackbone` records every call.** Tests can assert on
   `last_prompt` and `call_count` without ever touching the network. The
   `MODEL_LOAD_LLM=0` env-swap is a clean way to make CI deterministic
   without polluting the production code path.

4. **The Vietnamese prompts are a single source of truth.** Putting the four
   templates in `prompts_vi.py` with one constant per task (and the
   `get_prompt(task)` accessor) means a translator can iterate on the
   prompts without touching loader or service code. This is the right
   abstraction.

5. **Spec D1 (strict=False + shape matching) is correctly implemented.**
   `_load_nsp_weights` strips the `bert.` prefix, resizes embeddings to
   `ck_vocab=38168`, filters by shape, and loads with `strict=False` — all
   exactly as the design spec requires. The `test_load_project_checkpoint_keeps_decoder_weights`
   test mirrors this and asserts the loaded weights are non-zero.

6. **The completed plan has the required "Verification at archive time"
   section** at `docs/exec-plans/completed/model-002-model-loader.md:89`,
   which is what `docs/PLANS.md` mandates. The 2026-07-04 entry records the
   green run.

## Recommendations for Next Steps

1. **Fix C4 FIRST** — this is a blocker. The loaded CoherenceNet cannot score
   real Vietnamese text. Obtain the 38168-vocab tokenizer that matches the
   pre-trained checkpoint. If unavailable, derive it from
   `bert-base-multilingual-cased` vocab using the checkpoint's token mapping,
   or clamp out-of-range IDs to 0 (UNK) as a short-term workaround.
2. **Fix C1, C2, C3 before the next plan** that wires this layer to
   `svc-001..svc-004`. The bug in C1 will produce visibly bad summaries
   on `meeting_ami.json`; C2 will produce wrong speaker attributions; C3
   will OOM a real 4-bit LLM run.
3. **Add a smoke test that asserts the loaded NSP weights are non-zero** and
   that the resolved device is what the plan claims (catches I3).
4. **Add an `eval_vi`-shaped test fixture** that includes inline
   `{vocalsound}` / `{disfmarker}` annotations, so the placeholder regex
   bug (C1) is caught the next time anyone changes it.
5. **Add a test that tokenizes real Vietnamese text and verifies all token
   IDs are within the model's embedding range.** This catches the C4 bug
   mechanically.
6. **Promote the C2 fix to a Types-layer invariant** if possible: have
   `Utterance` carry the original index even if dropped, so the
   renumbering is impossible to do accidentally in any repo.
7. **Move `docs/QUALITY_SCORE.md` row to "35/38" or "45/45"** to match the
   real test count, and reword the "loads on cuda" claim to "loads on the
   resolved device (cuda preferred)".
8. **Record the C1/C2/C3/C4 fixes in `docs/exec-plans/tech-debt-tracker.md`**
   as Major items (the policy in `docs/PLANS.md` says Important or
   Critical issues should open a follow-up plan, not just be deferred).
9. **Don't merge until C4 and C1 are fixed** — C4 means the model can't
   score real Vietnamese text at all, and C1 produces wrong output on real
   data that the next agent will have to debug.

---

## Verdict

**Not ready to merge.** The Repository layer's skeleton is right, the
layer-rule enforcement is a real win, and the model-load contract is the
shape the Service layer needs. But four concrete correctness bugs (C1, C2,
C3, C4) mean the layer currently produces data the next agent will not trust
— and C4 means the CoherenceNet literally cannot score real Vietnamese text.
The fix surface is small for C1/C2/C3 (~10 lines total), but C4 requires
locating or deriving the matching 38168-vocab tokenizer. Don't proceed to
`svc-001` until at least C4 and C1 are resolved.
